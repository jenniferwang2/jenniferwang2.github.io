BACKEND FROM FIRST PRINCIPLES · POST 02

Read me first

The whole map, before any single piece of it

Thirty-one topics, organised the way I wish someone had organised them for me. Languages and frameworks change; the mechanics underneath them don't. Learn the mechanics and you can pick up any framework in weeks. Learn only a framework and you're stuck the moment you have to switch.

Why this order

Backend engineering is not just about building basic CRUDdy APIs. It's about building systems that are reliable, scalable, fault-tolerant and maintainable. Most people learn this piecemeal, through bootcamps, online courses and years of trial and error.

Most tutorials also teach these concepts through the lens of one specific framework: Express, Spring Boot, Rails. That creates blind spots. If your company suddenly needs to migrate from Rails to Go, how much of what you know is actually transferable, versus tied to the framework you happened to learn first?

This roadmap is built from books, open-source codebases, and years of hitting these gaps directly. It's grouped into seven arcs, and the order is deliberate: each arc assumes the one before it.

Seven arcs, one spineThe arcs stack: you can't reason about middleware ordering until you know the request pipeline, and you can't design a business logic layer until you know where data lives. Security runs alongside all of them rather than sitting at the end, for the reason in the last post.

Arc A · the whole picture first

1 · A high-level overview

Before diving into any one piece, start with the full picture: what actually happens when a request leaves a browser, hops across the network and through firewalls, reaches a backend server sitting somewhere on AWS, and comes back as a response. This section is about building a mental model of client-server communication before zooming into any single layer.

Arc B · how data moves

2 · HTTP protocol

The protocol underlying almost everything else: how HTTP messages are structured, the different header types (request, response, general, security), the core methods and when each applies. From there: CORS and preflight requests, response structure and status codes, HTTP caching with ETags and max-age, the differences across HTTP 1.1, 2.0 and 3.0, content negotiation, persistent connections, compression (gzip, deflate, brotli), and the security layer with SSL, TLS and HTTPS.

3 · Routing

How URLs map to server-side logic, and how routing ties into HTTP methods. Route components (path versus query parameters), route types (static, dynamic, nested, wildcard, regex-based), API versioning strategies and deprecation, route grouping for shared middleware and permissions, route security, and performance tuning for route matching.

4 · Serialization and deserialization

How data gets translated into a transportable format on the way out and back again on the way in. Text-based formats (JSON, XML) versus binary (Protobuf) and their performance trade-offs, JSON structure and data types, common pitfalls (missing fields, null handling, date and timezone issues), error handling, security concerns including injection risks and schema validation, and the readability-versus-performance trade-off.

Arc C · the request pipeline

5 · Authentication and authorization

Stateful versus stateless auth, basic auth, token-based auth, sessions, JWTs, cookies, OAuth and OpenID Connect, API keys, multi-factor auth, hashing and salting, and access control models (RBAC, ABAC). Plus the security practices around them: secure cookies, CSRF, XSS and MITM prevention, audit logging, obscuring auth error messages so they don't leak information, consistent failure responses, rate limiting and lockouts, and timing-attack prevention.

The distinction this whole section rests on

Authentication is who are you. Authorization is what are you allowed to do. They fail differently, they're attacked differently, and conflating them is how most access control bugs happen.

6 · Validation and transformation

The validation layers: syntactic (is this a valid email, phone, date), semantic (a birthdate can't be in the future), and type validation. Client-side versus server-side, and why server-side is the real security boundary. Transformation concerns like type casting, date normalisation and lowercasing emails. Sanitisation, relational validation (password and confirmation matching), conditional and chained validation, and handling errors gracefully with meaningful messages, aggregated errors, and no leaking of internals.

7 · Middlewares

What middleware is and where it sits in the request lifecycle, how chains and ordering work (logging → auth → validation → routing → error handling), how the "next" function works, and how middleware can short-circuit a request. Common types: security headers, CORS, CSRF protection, rate limiting, auth, logging and observability, error formatting, compression, and body parsing including multipart uploads. Plus ordering and performance practices.

8 · Request context

The request-scoped metadata flowing through middleware, controllers and services. It is temporary state tied to one request lifecycle. What lives there (HTTP metadata, user info injected during auth, trace IDs, cached permission checks), the use cases (auth, rate limiting, tracing, logging), how it interacts with middleware, timeout handling, and keeping it lightweight enough to avoid memory leaks and tight coupling.

Arc D · shaping the application

9 · Handlers, controllers and services

The MVC-style breakdown of responsibilities, how middleware removes duplicate logic across handlers, and how to centralise error handling so success and error response formats stay consistent.

10 · CRUD deep dive

How CRUD maps onto HTTP methods and status codes (POST → 201/400, GET for single and list resources, PUT and PATCH for updates, DELETE for removal). Pagination, search, sorting and filtering. Plus the practices: strict validation, consistent formatting, limiting payload size, redacting sensitive fields, and proper auth handling.

11 · RESTful architecture and best practices

Designing around resources rather than actions, sticking to HTTP semantics, versioning approaches (URI, header, query string, media type), designing with OpenAPI in mind, content negotiation, meaningful error messages, client-side caching via ETags, and optimising large payloads.

12 · Databases

Relational versus non-relational and when each applies, ACID properties and the CAP theorem, querying and joins, schema design and indexing, query optimisation, caching and connection pooling. Also data integrity through constraints, transactions and concurrency, ORMs and their trade-offs, and migrations.

13 · Business logic layer

Where this sits in the request lifecycle: after the presentation layer (routing, middleware, validation, handlers) and before data access. Design principles (separation of concerns, single responsibility, open-closed, dependency inversion), the core components (services, domain models, business rules, business-level validation), service layer design, and how errors should propagate upward.

Arc E · everything around the request

14 · Caching

Why caching matters and how it differs from database persistence. Types (memory, browser, database, client-side, server-side), strategies (cache-aside, write-through, write-behind, read-through), eviction policies (LRU, LFU, TTL, FIFO), and invalidation approaches (manual, TTL-based, event-based). Multi-level caching, caching for web apps, database query caching, and tracking hit and miss ratios.

15 · Transactional emails

Common use cases and the anatomy of a transactional email (subject line, preheader, header, body, call to action, footer), and how to personalise content with dynamic data.

16 · Task queuing and scheduling

Use cases for queuing: sending emails, image processing, third-party API calls, payment processing, webhooks, and offloading heavy batch work so the user isn't left waiting. Scheduling for backups, recurring notifications, data sync and cleanup. Core components (producer, queue, consumer, broker), task dependencies, concurrent task groups, retry and error handling, and prioritisation, such as payment processing ahead of notifications.

17 · Elasticsearch

Why and how it's used: inverted indexes, term frequency, inverse document frequency, segments and shards. Use cases like type-ahead search, log analytics and full-text search. Creating and managing indexes, query types, relevance scoring, performance tuning (text versus keyword fields, analysers, boosting, pagination), advanced patterns (filtering, aggregation, fuzzy search), Kibana, and practices like explicit field mappings and avoiding wildcard queries.

25 · Object storage and large files

Common use cases such as S3, handling large files via chunking and streaming, and multipart uploads.

26 · Real-time backend systems

WebSockets, server-sent events, and pub/sub architecture.

Arc F · running it in the real world

18 · Error handling

Categories of errors (syntax, runtime, logical) and strategies (fail-safe, fail-fast, graceful degradation, prevention). Catching errors early, avoiding silent failures, custom error types, logging with stack traces, global handlers, user-facing messages that are actionable without leaking internals, and monitoring tools like Sentry and the ELK stack.

19 · Config management

Separating environment-specific settings from application logic: managing environments, safely handling sensitive values (API keys, database passwords, certificates), and toggling features without redeploying. Types of config (static, dynamic, sensitive), sources (env files, JSON, YAML), and the trade-offs between environment variables, CLI flags and static files.

20 · Logging, monitoring and observability

The distinctions between logging, tracing, monitoring and observability. Logging types (system, application, access, security) and levels, structured versus unstructured logs, and practices like centralised logging, rotation and retention, contextual logs, and never logging sensitive data. Monitoring types (infrastructure, APM, uptime), tools like Prometheus and Grafana, and alerting that avoids fatigue. Plus observability's three pillars (logs, metrics, traces) and the compliance side of log management.

21 · Graceful shutdown

Why it matters during restarts, autoscaling, microservice updates and long-running jobs, and how it works mechanically: signal handling (SIGTERM and SIGKILL) and the shutdown sequence: stop accepting new requests, finish in-flight ones, close external connections, terminate.

23 · Scaling and performance

Performance metrics (response time, resource utilisation) and bottleneck identification. Database optimisation covers avoiding N+1 queries, proper joins, lazy loading and indexing hot fields, plus batch processing, avoiding memory leaks, reducing network overhead via compression, and profiling. Practices: clear code over premature optimisation, modular systems, graceful degradation under load, and offloading non-critical work.

24 · Concurrency and parallelism

The distinction between the two: concurrency for I/O-bound work, parallelism for CPU-bound work.

27 · Testing and code quality

Testing types: unit, integration, end-to-end, functional, regression, performance, load and stress, user acceptance, and security testing. Test-driven development, automating tests in CI/CD, linting and formatting, and quality metrics like cyclomatic complexity and maintainability index.

The spine · runs through everything

22 · Security

Common attack vectors (SQL and NoSQL injection, XSS, CSRF, broken auth, insecure deserialization) and secure design principles: least privilege, defense in depth, fail-secure defaults, separation of duties, security by design. Input validation and sanitisation, rate limiting, content security policy, CORS, same-site cookies, and event monitoring.

Why this has a number but isn't really a chapter

Listing it as §22 is a convenience. In practice it belongs everywhere: injection is a §6 validation problem and a §12 database problem, CSRF is a §5 auth problem and a §7 middleware problem, and information disclosure is a §18 error-handling problem. Every post in this series ends with where the thing breaks, because a vulnerability list you can recite is not the same as knowing where the risk lives in your architecture.

Arc G · standards and delivery

28 · The 12-factor app

A set of foundational principles for building maintainable, deployable applications.

29 · OpenAPI standards

Why standardisation matters for documentation, automation and the tooling ecosystem: Swagger, Redoc, Postman. The history from Swagger to OpenAPI, active spec versions, and core document structure including metadata, paths, components, security definitions and responses. Plus features in 3.0 and 3.1, tooling, and API-first development where you write the spec before the implementation.

30 · Webhooks

Use cases like notifications and third-party integrations. Webhooks versus polling: server-initiated push against client-initiated pull. Key components (webhook URL, event triggers, payload, HTTP method, response handling), practices (signature verification, HTTPS, retry logic, logging), testing with tools like ngrok, and real examples from Stripe, GitHub, Slack, Discord and Twilio.

31 · DevOps for backend engineers

Continuous integration, delivery and deployment. Practices including infrastructure as code, config management and version control. Tooling: Docker for containers, Kubernetes for orchestration, CI/CD pipelines, scaling approaches (horizontal versus vertical), and deployment strategies like blue-green and rolling.
