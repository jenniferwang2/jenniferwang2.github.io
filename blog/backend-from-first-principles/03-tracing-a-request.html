Zero

Start here: the ten words you need

Everything below assumes you know nothing. If you already know what an IP address is, skip to section one — but the rest of this guide leans on these ten ideas constantly, so it's worth thirty seconds each.

The vocabulary, in plain English

Read these as a set. They build on each other: a computer has an IP address, runs processes, which listen on ports, which you reach using a protocol, after a domain name is translated by DNS.

1 · Client and server

A client is whatever asks. A server is whatever answers. That's the whole distinction — it's a role in a conversation, not a type of hardware. Your laptop is a client when you browse, and could be a server if you ran software on it that answered requests. The words describe who spoke first.

2 · A server is a real computer

Not a cloud, not an abstraction. A physical machine sitting in a warehouse somewhere, plugged into power and a network, that never gets turned off. When this guide says "AWS EC2 instance," it means a slice of one of those machines that Amazon rents you by the hour.

3 · IP address

A number that identifies one machine on a network, written like 54.175.148.96. Think of it as a street address. Every machine reachable on the internet has one. Humans are bad at remembering them, which is the entire reason domain names exist.

4 · Domain name

The human-readable label — google.com, backend-demo.sriniously.xyz. It is not an address. It is a name that has to be looked up to find the address, the same way a contact name in your phone has to be looked up to find the number.

5 · DNS

The system that does that lookup. Domain Name System — the internet's phone book. You give it a name, it gives you back an IP address. This happens before anything else in every request you've ever made, invisibly, in milliseconds.

6 · Process

A program that is currently running. Not the file on disk — the live thing in memory doing work. Your browser is a process. A web server is a process. One computer runs hundreds at once. Each gets a number called a PID (process ID) so the operating system can tell them apart.

7 · Port

A number between 0 and 65535 that identifies which process on a machine you want to talk to. The IP address gets your message to the building; the port number gets it to the right apartment. A process "listens on" or "binds to" a port, meaning it has claimed that number and will be handed anything addressed to it.

8 · Protocol

An agreed format for the conversation. Both sides have to have decided in advance what a message looks like, or neither can parse the other. HTTP is the protocol of the web. TCP is the lower-level one underneath it that guarantees the bytes arrive in order.

9 · Request and response

One round trip. The client sends a request (a chunk of text saying what it wants and some extra information about itself), the server sends back a response (a status number, some extra information, and usually a body of content). Everything in this guide is one request and one response, traced in slow motion.

10 · Headers and body

Both requests and responses have two parts. Headers are the metadata — small labelled lines like Content-Type: application/json that describe the message. The body is the actual payload: the HTML, the image bytes, the JSON. Headers are the envelope; the body is the letter.

The analogy this whole guide runs on

A request is a letter. DNS is looking up the address in a directory. The firewall is the security desk in the lobby deciding which deliveries are even allowed in the building. Nginx is the receptionist inside who reads who the letter is addressed to and walks it to the right office. The app process is the person in that office who opens it, does something, and writes a reply. Nothing about the internet is more complicated than that — it's just that each of those four steps has its own jargon.

Two conventions used throughout

Things written like this are literal — a command you'd type, a filename, a piece of configuration, an address. You could copy them.

The word "hop." A hop is one leg of the journey — one place the request stops before moving on. This guide breaks the trip into five hops and gives each one a numbered heading.

One

What is a backend?

Let's picture it. A backend in its traditional definition is a computer which is listening for HTTP or WebSocket or gRPC or any other kind of request through an open port — whether it is 80 or 443 — which is accessible over the internet, so that clients or other frontends can connect to it, send data to it, or receive data.

That sentence, decoded

It's one long sentence with five pieces of jargon in it. Taken apart:

"a computer which is listening"
A program is running that has told the operating system: if anything arrives addressed to me, wake me up. It then sits idle, doing nothing, possibly for days. That waiting state is what "listening" means. It is not actively checking anything.
"for HTTP or WebSocket or gRPC"
Three different formats the incoming message might be written in. See the second diagram below — the differences don't matter yet.
"through an open port"
"Open" means two things had to happen: the program claimed the port number, and the firewall was configured to let outside traffic through to it. Either one missing and it's closed.
"whether it is 80 or 443"
The two conventional port numbers for web traffic. 80 is unencrypted, 443 is encrypted. They're conventions, not laws — but the entire internet agreed on them, so everything assumes them.
"accessible over the internet"
The crucial qualifier. A program listening on a port on your laptop is a server, but only your laptop can reach it. Being on the public internet with a public IP address is what makes it useful to strangers.

And the name is literal:

We call it a server because it provides, or it serves, some kind of content — whether it is static files like images or JavaScript files or HTML files, or it could be JSON. And it also accepts data if the client sends something.

"Static files" versus "JSON"

Static files are files that already exist on disk and get sent back byte-for-byte, unchanged, to everyone who asks. An image, a stylesheet, a logo. "Static" means nothing is computed — the server just reads the file and hands it over, like a photocopier.

JSON (JavaScript Object Notation) is a text format for structured data. It looks like this: {"name": "Ada", "id": 42}. It's how one program sends data to another program in a way both can parse. It is generated fresh per request, usually from a database, which is why it's the opposite of static. When an app "calls an API," JSON is almost always what comes back.

Analogy

Serving static files is a vending machine: same slot, same item, every time. Serving JSON is a kitchen: you order, someone reads the order, assembles something specific to you, and hands it over. Same building, very different work.

The definition, drawnFour literal claims: it is a computer, a process on it is bound to a port, that port is reachable from the internet, and it both serves content and accepts data. Everything later in this guide is machinery around those four facts.

The three protocols named in the definitionThe video lists HTTP, WebSocket and gRPC together because from the server's point of view they're the same situation — a process bound to a port, waiting.

The three protocols, for someone who's never met them

HTTP — "stateless" and "one shot"
One shot: you ask, you get an answer, the conversation ends. Want something else? Start a brand new conversation. Stateless: the server remembers nothing about you between requests. Each one arrives as if from a total stranger. (Logins work by the client re-presenting a token every single time — the server isn't remembering, you're re-introducing yourself.)
WebSocket — "persistent" and "both sides push"
The line stays open. Crucially, the server can now speak first, which plain HTTP cannot do. That's what makes live chat and live scoreboards possible without the client asking "anything new?" every second.
gRPC — "binary" and "typed"
Binary means the message is packed bytes rather than readable text — smaller and faster to parse, but you can't eyeball it. Typed means both sides agreed in advance on the exact shape of every message, so mismatches get caught early. It's "mostly internal" because it's used between a company's own servers, not between a browser and a server.

Analogy

HTTP is sending a letter and getting one back. WebSocket is a phone call left off the hook — either party can talk whenever. gRPC is two colleagues who've agreed on a shorthand notation nobody else can read, because they only ever talk to each other and want to be fast.

Why those two numbers specifically

A machine has one IP address but runs many services. Ports multiplex: the IP gets you to the machine, the port gets you to the right process on it. Typing https:// silently appends :443; http:// appends :80.

Unpacking that

"Multiplex" just means "let many things share one channel by labelling them." One wire, many conversations, kept apart by a number.

"Silently appends" is worth pausing on, because it explains an oddity you've seen your whole life. The full address of a web page is really https://example.com:443/page. You never type the :443 because your browser fills it in for you whenever you write https://. If a site ran on an unusual port you'd have to type it yourself — which is why developers' local addresses look like localhost:3000.

HTTP vs HTTPS: the S is "secure," meaning the contents are encrypted in transit so anyone intercepting the wire sees scrambled bytes instead of your password. The encryption system is called TLS (you may see the older name, SSL). That's why 80 and 443 are separate ports: they're the same conversation, one shouted in public and one in code.

Analogy

The IP address is the street address of an office tower. The port is the suite number. Port 443 is the suite everyone knows the reception desk is in, so nobody bothers writing it on the envelope.

This one fact is the spine of the whole article.
Two

How backends work

I want you to get a holistic view — to actually see the components physically, how they work behind the scenes. So let's go through this whole flow. I have a backend server which is deployed in AWS, so let's take that as an example.

What "deployed in AWS" means

AWS (Amazon Web Services) rents computers by the hour. You don't buy a machine or find somewhere to keep it; you click a button and a few seconds later you have a computer in a data centre with an IP address, which you pay for until you switch it off.

EC2 is the specific AWS product for "give me a plain computer." An EC2 instance is one such rented machine. It's a virtual machine — a software-simulated computer sharing real hardware with other customers' simulated computers, kept strictly separated. From inside, it is indistinguishable from a real machine.

Deployed means "copied onto the server and started running there," as opposed to running on the developer's laptop.

Analogy

Renting an EC2 instance is renting a desk in a co-working space rather than buying an office. The building, power and internet are someone else's problem; you just show up and work. And you can hand the desk back at 4pm and stop paying.

What "DevTools" is, and how to open it yourself

DevTools (developer tools) is a panel built into every browser that shows you what the page is actually doing underneath. Press F12, or right-click anywhere on a page and choose Inspect. The Network tab lists every single request the page made, with the headers and the response body for each.

01

DNS

turning a name into an address

The first thing that you can see is the domain name. So the first thing that comes to mind is, we should take a look at our DNS server.

Words in this hop

Registrar
The company you buy a domain name from. Domain names are rented annually, not owned. The registrar also gives you a control panel where you say which IP address the name should point to — that's the screenshot below.
DNS record
One line in that panel. A record has a type (what kind of answer it gives), a host (which name it applies to) and a value (the answer). The world's DNS servers read these and repeat them to anyone who asks.
Subdomain
In backend-demo.sriniously.xyz, the part backend-demo is a subdomain of sriniously.xyz. You own the whole domain, so you can invent as many subdomains as you like for free and point each anywhere. That's why one person can run both a "frontend" and "backend" address.
Nameserver
A computer whose job is answering DNS questions. There is no single one — there are millions, arranged in a hierarchy, which is the second diagram in this hop.

Row by row, since most of these look cryptic

@ in the Host column
Shorthand for "the domain itself, with nothing in front" — i.e. sriniously.xyz rather than something.sriniously.xyz. It's a convention, not a symbol with meaning.
The two rows pointing at 54.175.148.96
This is the punchline of the whole guide, stated early. Two completely different-looking web addresses — the "frontend" and the "backend" — resolve to the same single computer. They are not two servers. Section four shows how one machine tells them apart.
CNAME
Canonical Name. An alias. Instead of answering with an address, it answers with another name you now have to look up. Used when the final IP isn't yours to know — a hosting company may change their servers' addresses whenever they like, and a CNAME means you never have to update anything.
TXT
A free-text note attached to your domain. It does nothing for routing. Since only the domain's owner can add one, other companies use it as proof of ownership: Google says "put this exact string in a TXT record," and if it appears, you evidently control the domain.
SPF
Sender Policy Framework — a TXT record listing which mail servers are allowed to send email claiming to be from your domain. It exists because email, by default, lets anyone write any return address they like. Unrelated to web traffic, but it lives in the same panel, which is why it's in the screenshot.

To oversimplify it, DNS has different types of records. You can use A records to point to a particular IP, and you can use CNAME records to point to a particular domain name or subdomain.

The difference that mattersAn A record ends the chase. A CNAME hands you another name to chase, which is why it's used when you don't control or can't predict the final address.

Where a lookup actually goesMost lookups never leave your machine, because something already has the answer cached. TTL is what controls how long each of these layers may hold on to it.

Caching, resolvers, and TTL

Cache (rhymes with "cash") means a saved copy of an answer, kept so you don't have to ask again. Caching is everywhere in computing and it is the single biggest reason anything feels fast.

Resolver is the name for whoever does the legwork of chasing a DNS answer down. Usually it's run by your internet provider. Your browser asks it, and it either already knows or goes on the hunt shown in the diagram.

TTL — Time To Live — is a number of seconds attached to every DNS answer meaning "you may keep this copy for this long, then throw it away and ask again." It's the reason changing a DNS record doesn't take effect instantly for everyone: caches all over the world are still repeating the old answer until their TTL expires.

Root nameserver / TLD server / authoritative NS are the three rungs of the hunt. TLD is Top-Level Domain — the last chunk of a name, like .com, .org or here .xyz. Authoritative means "this one isn't repeating what it heard; this one holds the actual record and its answer is final."

Analogy

Finding a phone number for someone in a huge organisation. You check your own contacts (browser cache), then the sticky note on your desk (OS cache), then ask the office manager (your resolver). If nobody knows, the office manager rings the main switchboard, which says "that's the Glasgow branch," which says "that's the accounts team," who finally give the actual number. And then everyone writes it down, so nobody has to do that again this week. The TTL is how long they trust their note before binning it.

Security note · DNS is the first hop

Because DNS resolves before TLS is negotiated, an attacker who controls the answer controls where your traffic goes. Hijacking changes the record at the registrar; cache poisoning feeds a resolver a forged answer. DNSSEC signs responses so tampering is detectable — and the panel in the screenshot shows it toggled off.

Why that note is scarier than it sounds

TLS is the encryption that makes the padlock icon appear. It also verifies you're really talking to the site you asked for. But — and this is the point — DNS happens first. If someone feeds your computer a false answer at the DNS stage, you connect to their machine believing it to be the real one, and they can present their own valid padlock for a lookalike domain. The encryption worked perfectly; it just encrypted your conversation with the wrong person.

Cache poisoning is slipping a forged answer into one of those caches from the previous diagram, so everyone using that resolver gets sent the wrong way. DNSSEC adds a cryptographic signature to DNS answers so a forgery can be spotted. "Toggled off" means this particular domain has no such protection — which is extremely common and worth knowing.

The two IP addresses, and why there are two

A machine can have several addresses at once, on different networks, the way a person can have a street address and an internal desk extension.

Public IPv4 — 54.175.148.96
Reachable from anywhere on earth. This is the one DNS hands out. IPv4 is just the older, four-numbers-with-dots addressing scheme; IPv6 is the newer, longer one.
Private IPv4 — 172.31.87.253
Only meaningful inside Amazon's private network around your machines. Numbers starting 172.31., 10. or 192.168. are reserved for private networks worldwide — your home router almost certainly gave your laptop one. They are deliberately not routable on the open internet.

Appears in the diagram below. This address always means "this very machine, talking to itself." Traffic sent here never touches a network cable at all. Its nickname is localhost. Remember it; hop four depends entirely on it.
t2.micro
The size of the rented machine. vCPU = virtual processor core. 1 core and 1 GB of memory is tiny — less than a cheap phone — and it's free for the first year, which is why tutorials use it.

Analogy

Public IP: your building's postal address, known to the world. Private IP: your desk number, meaningful only to colleagues inside. Loopback: writing yourself a note and putting it in your own pocket — it never leaves you.

Three tiers of reachabilityEach ring is narrower than the one outside it. The innermost — loopback — is the one Nginx uses to hand a request to the app, which is why the app never needs a publicly open port.

Security note · IMDSv2

EC2 instances can query 169.254.169.254 for their own metadata, including temporary IAM credentials. Under IMDSv1 a plain GET sufficed, making it a devastating SSRF target — trick a server into fetching that URL and you walk away with its cloud credentials. That was the mechanism in the 2019 Capital One breach. IMDSv2 requires a session token obtained by PUT first, which a naive SSRF can't produce.

VPC, SSRF, IAM — decoded

VPC
Virtual Private Cloud. Your own private network inside Amazon, walled off from other customers'. Machines in it can talk to each other by private IP; nothing outside can reach in unless you allow it.
IAM credentials
Identity and Access Management — Amazon's permission system. Credentials are the keys that prove "I'm allowed to read those files / start those machines." Stealing them means acting as the company inside their own cloud account.
The metadata address
169.254.169.254 is a magic address every EC2 machine can ask about itself. Handy — it's how a server learns its own configuration without hardcoding it. Dangerous — because the answer includes live credentials.
SSRF
Server-Side Request Forgery. You trick a server into making a request on your behalf. Say a site has a "fetch the image at this URL" feature; you give it that magic metadata address instead, and it obediently fetches the credentials and shows them to you. The server had permission, you didn't, and you borrowed its hands.
GET and PUT
Two HTTP verbs — the first word of every request. GET means "give me this," PUT/POST mean "here's some data." The fix works because the naive attack can usually only make the server perform a simple GET, and the newer version demands a two-step handshake starting with a PUT.

Capital One, 2019: exactly this chain, real-world, roughly 100 million customer records.

03

The firewall

before it reaches the computer

Before it reaches our server, or the particular computer, it goes through a firewall which is the AWS native firewall. The firewall has to allow some kind of request to go through.

Firewall, security group, inbound, dropped

A firewall is a filter sitting in front of a machine that inspects arriving traffic and decides whether to pass it on. In AWS the firewall is called a security group — a list of rules attached to your machine. Same idea, Amazon's name for it.

Inbound rules govern traffic coming toward your machine; outbound rules govern traffic your machine sends out. The screenshot shows three inbound and one outbound.

Dropped is a deliberate word. The packet isn't rejected with an error message — it's silently discarded, and the sender gets nothing at all, just a timeout. That's preferable, because an error reply would confirm that a machine exists there and is refusing you. Silence tells an attacker nothing.

A packet is one small chunk of data travelling the network. Big messages get chopped into many; the firewall inspects each one.

Analogy

A nightclub with a guest list and a bouncer. The list names who gets in (ports 22, 80, 443); everyone else is turned away at the pavement, without explanation, and never learns whether the club is even open. Note the direction of the logic: the list says who's allowed, not who's banned — so anyone forgotten is, by default, out.

0.0.0.0/0 is CIDR notation for every IPv4 address in existence. Source: anywhere.

CIDR, and the "Protocol: TCP" column

CIDR (say "cider") is a compact way of writing a whole range of IP addresses. The number after the slash says how many leading bits are fixed: the higher the number, the narrower the range. /32 is exactly one address; /0 fixes nothing, so it matches all four billion. Writing 0.0.0.0/0 as a source means let anyone on earth try.

TCP — Transmission Control Protocol — is the layer beneath HTTP. It handles the unglamorous work: chopping data into packets, numbering them, re-sending lost ones, reassembling them in order. HTTP is the language of the conversation; TCP is the reliable phone line it happens over. The firewall works at the TCP level, which is why it can see port numbers but not what you're saying.

If we don't allow these two ports — like 443 for allowing HTTPS traffic or 80 to allow HTTP traffic — if you don't allow it, AWS will block it right there and our request won't be able to reach our server.

Default deny, drawnYou enumerate what's permitted; everything else is dropped upstream of the machine. Note port 3001 in red — the app's own port is not reachable from outside, by design.

Why 3001 is deliberately absent

The Node app listens on 3001, but nobody outside can reach it. The only path in is 80/443 → Nginx → loopback → 3001, and loopback traffic never leaves the machine. One narrow front door; everything else internal.

Security notes · these specific rules

SSH open to 0.0.0.0/0 is the weak point. Open port 22 to the world invites constant automated brute-force. Better: restrict the source range, use a bastion, or drop port 22 entirely in favour of AWS Systems Manager Session Manager.

Security groups are stateful. Allow a connection inbound and its response is automatically permitted back out. Network ACLs, the other AWS firewall layer, are stateless and need rules in both directions.

Brute force, bastion, stateful

Automated brute-force
Programs that roam the internet trying every address, and on any machine with port 22 open, guessing usernames and passwords thousands of times an hour, forever. This is not targeted — it happens to every exposed server within minutes of it coming online. Use key-based login instead of passwords and it's survivable; use a weak password and it isn't.
Bastion (or jump box)
One heavily locked-down machine that is the only thing allowed to be reached from outside. You log into it, and from there into everything else. One door to defend instead of twenty.
Stateful
The firewall remembers connections it already approved. If it let your request in, it automatically lets the reply back out — you don't write a second rule for the return trip. Stateless filters have no memory, treat every packet as unrelated, and so need rules for both directions. Stateful is the friendlier default and the reason the outbound column in the screenshot looks so empty.

Analogy

A stateful firewall is a receptionist who signs you in and, remembering your face, waves you out without ceremony. A stateless one is a turnstile that checks a ticket in each direction and has no idea you're the same person.

04

Nginx

the reverse proxy

We are using something called a reverse proxy, which basically means it is a server which sits in front of other servers, so that we can manage different types of redirects or configs from a centralized space instead of changing the configs in every single server.

"Reverse" proxy — reverse compared to what?

A proxy is any middleman that passes messages along on someone's behalf. A forward proxy sits in front of you and makes requests for you — a VPN or a corporate web filter. A reverse proxy sits in front of the servers and receives requests on their behalf. Same job, opposite end of the wire. "Reverse" only tells you which side it's protecting.

Nginx (pronounced "engine-X") is the most common piece of software for doing this. It is itself just another process listening on a port — there's nothing exotic about it. It happens to be the one holding 80 and 443.

The quote mentions "configs" — short for configuration: text files that tell a program how to behave, edited by hand and re-read when the program restarts. Hop four's screenshots are literally these files.

Analogy

The reverse proxy is the receptionist in a shared office building. Every visitor arrives at one desk. The receptionist checks who they're here to see, and walks them to the right office. The people in the offices never deal with the front door, never check ID, never learn the building's security procedures — and if the procedures change, one person learns the new version, not forty.

What the proxy buys youThe blocking constraint on the left is physical: only one process can bind to port 443. Everything else is convenience, but that one is a hard limit.

Certificates, Certbot, and "terminating TLS"

Certificate
A file proving that whoever holds it really controls a given domain name, signed by an organisation browsers already trust. It's what makes the padlock appear. Without one, browsers show a full-page warning. A Certificate Authority is one of those trusted signers.
Let's Encrypt and Certbot
Let's Encrypt is a free, automated Certificate Authority — its arrival is the main reason encryption became universal on the web. Certbot is the tool that talks to it: it proves you own the domain, fetches the certificate, edits your Nginx config for you, and renews it every couple of months. The # managed by Certbot comments mark lines a human didn't write. (Anything after # is a comment: a note for humans, ignored by the machine.)
Terminating TLS
"Terminate" here means "end" — the encryption stops at Nginx. Nginx does the decrypting, and hands the now-plain request onward to the app. The app therefore never has to know anything about certificates. This is safe only because the onward hop is over loopback, never touching a network.
Header
Recall from the primer: a small labelled line of metadata. The Host header is one the browser always sends, containing the domain name you typed. It's the critical one here — since both subdomains arrive at the same IP and port, that header is the only thing distinguishing them.

Analogy

Post arriving at a big office building. The street address gets everything to the same lobby (one IP, one port). The line on the envelope saying Attn: Accounts is the Host header. The mail clerk reads it and walks the letter upstairs. Two departments, one address, one envelope line telling them apart.

Line by line

server_name backend-demo.sriniously.xyz; — how one machine serves two subdomains. Nginx reads the Host header and picks the matching block. This is the answer to why DNS pointed both names at one IP.

proxy_pass http://127.0.0.1:3001; — forward to the app on this same machine, over loopback.

proxy_set_header X-Real-IP $remote_addr; — without this the app would think every request came from 127.0.0.1, because that is literally who is calling it.

listen 443 ssl; and the ssl_certificate lines — Nginx holds the certificate, decrypts inbound TLS, forwards plaintext internally. The app never touches a certificate.

return 301 https://$host$request_uri; — the second block's entire job. Anything on port 80 is redirected to HTTPS.

Those five lines, for someone who's never read a config file

Nginx configs are a list of instructions, one per line, each ending in a semicolon. Words beginning with $ are variables — placeholders Nginx fills in per request.

server_name
"This block of instructions applies to requests whose Host header is this." It's the label on the office door.
proxy_pass
"Forward this request to that address and send whatever comes back to the visitor." Everything in a reverse proxy ultimately reduces to this one line.
proxy_set_header X-Real-IP $remote_addr;
Add a header recording who the visitor actually was. This is necessary because of a genuinely confusing consequence: once Nginx forwards the request, it becomes the sender. From the app's point of view, every visitor on earth appears to be 127.0.0.1 — itself. Without this line the app couldn't log, rate-limit, or geolocate anyone. Headers starting X- are conventionally custom ones nobody standardised.
listen 443 ssl;
"Claim port 443 and expect encrypted traffic on it." (SSL is the old name for TLS; the keyword stuck.)
return 301
301 is an HTTP status code meaning "moved permanently." The browser follows the new address automatically and remembers to go straight there next time. Status codes are the three-digit numbers in every response: 200 is success, 301/302 are redirects, 404 is not found, 500 is the server broke.

The part that confused me initially was why Nginx forwards the request to localhost:3001. It simply means the backend is running on the same EC2 machine, and Nginx acts like a receptionist that forwards requests to the correct application.

The receptionistBoth subdomains resolve to the same IP and arrive on the same port. The Host header is the only thing distinguishing them, and matching it against server_name is the entire routing decision.

Security note · forwarded headers

X-Forwarded-For is trivially spoofable if an attacker can reach the app directly and the app trusts the header blindly. It is only safe to trust when traffic must pass through the proxy — which is exactly why port 3001 is closed at the firewall. The two controls depend on each other.

Why that's a real problem, concretely

X-Forwarded-For is the standard header carrying the original visitor's IP address through a proxy — the same idea as X-Real-IP above. Spoofable means anyone can simply type any value they like into it, because headers are just text the sender writes.

So: suppose your app blocks someone after five failed logins from one IP. If the attacker can reach the app directly, they set a fresh fake X-Forwarded-For on each attempt and your limit never triggers. The header is only trustworthy if the app is certain every request passed through Nginx, which rewrites it. That certainty comes entirely from port 3001 being closed at the firewall. Two separate settings, in two separate systems, that are only safe together — which is exactly the kind of thing that makes infrastructure hard.

05

The process

the final hop

If we take a look at our processes, let's do pm2 list. We can see here that we have two processes running — one for frontend and another for backend. And this is a Node server. So this is the final hop.

Node, PM2, PID

Node (Node.js)
A program that runs JavaScript outside a browser. JavaScript was invented for web pages; Node let it run as a normal server-side program. It's why the same language can appear on both sides of this article.
Express
A small library for Node that handles the fiddly parts of being a web server, so you write "when someone asks for /users, do this" instead of parsing raw HTTP by hand. It shows up later in a response header.
PM2 — a process manager
A program whose job is running other programs and keeping them alive: restarting them if they crash, starting them again after a reboot, collecting their output into log files. pm2 list is a command that prints a table of everything it's currently minding.
PID
Process ID — the number the operating system uses to refer to one running program. It changes every time the program restarts. Useful mainly for telling two processes apart, which is exactly what the screenshot does.

Running node server.js in a terminal fails four ways: it dies when the SSH session closes, it doesn't return after a crash, it doesn't start after a reboot, and there's no log management. A process manager solves all four. Alternatives are systemd units, Docker with a restart policy, or Kubernetes.

Why those four failures happen, and what the alternatives are

When you log into a server over SSH and type a command, that program is the child of your login session. Close the session and the operating system kills it — it assumes you're done. So a server started by hand dies the moment you disconnect, which surprises everyone once.

The other three are just as mundane: programs crash and stay dead; rebooted machines start nothing on their own; and anything a program prints is thrown away unless someone catches it. A process manager is simply a babysitter that solves all four.

systemd
The service manager already built into most Linux systems. A "unit" is a small file describing how to start something and when. No extra software needed.
Docker
Packages an app together with everything it needs into a container — a sealed box that runs identically anywhere. "Restart policy" means the same babysitting, configured in one line.
Kubernetes
The same idea at large scale: it runs containers across many machines, restarting and moving them automatically. Vastly more capable and vastly more complicated. Overkill here.

What curl is

curl is a command-line tool that makes an HTTP request and prints the response as text. No browser, no page rendering, no JavaScript — just the raw exchange. It's the standard way to check "is this thing actually answering?"

The command curl localhost:3001/users means: from this machine, ask the process on port 3001 for the path /users. Notice what it skips. No domain name, so no DNS. It never leaves the machine, so no firewall. It goes straight to 3001, so no Nginx. All four hops bypassed — and the answer is identical. That is the proof that everything before it was infrastructure rather than substance.

Analogy

Ordering from a restaurant through a delivery app, versus walking into the kitchen and asking the chef directly. Same food. The app, the driver and the front-of-house staff were never part of the cooking — they were the delivery mechanism. And you can only walk into the kitchen if you're already in the building, which is the whole reason the front door exists.

The layering, made visibleStrip away DNS, the firewall and the proxy and the app still answers — you just have to be standing on the machine to ask it.

Reading the whole journey backwards from the evidence

So if we were to summarize: our request starts here in the browser, it goes to our DNS server, then that goes to our AWS servers, and it goes through a firewall, and that reaches our AWS instance. And that request then reaches Nginx, and that finally forwards that request to our localhost 3001, our final server.

CVEs, and those three missing headers

A CVE (Common Vulnerabilities and Exposures) is a publicly catalogued security flaw with an ID number. The catalogue is open on purpose, so defenders can patch. The side effect: if a server announces "nginx 1.24.0," anyone can look up that exact version's known flaws in seconds. Saying less is free defence — hence "information disclosure," the category of leaking details that are individually harmless but collectively a map.

Strict-Transport-Security (HSTS)
Tells the browser "for this site, never use unencrypted HTTP again, even if asked." Closes the gap where your very first visit goes over port 80 before the redirect fires — the one moment an attacker on the network could intercept.
Content-Security-Policy (CSP)
A list of which sources the page is permitted to load scripts from. If an attacker manages to inject a malicious script tag, the browser refuses to run it because the source isn't on the approved list. The main defence against a large class of attacks called XSS (cross-site scripting).
X-Frame-Options
Stops other websites from embedding your page invisibly inside theirs and tricking users into clicking things they can't see — an attack with the excellent name clickjacking.

All three are single lines of config. "Absent" means nobody added them, which is the normal state of most of the internet.

Three

Why do we need backends?

Imagine you're scrolling through your Instagram feed and you come across your friend's post. As usual you like them, you click on the like button, and on the other side your friend gets a notification that you liked their post. So between you clicking on the like button and your friend getting the notification — what exactly happened?

Seven steps, five of which only a server can doIdentify the caller, authorize the action, persist the fact, look up a different user's data, and trigger something on a device you have no access to. Your phone can do none of these on its own.

The five server-only steps, in plain terms

Authenticate
Who are you? Checking that whoever sent this really is the account they claim. Your phone can assert "I'm user 88" — but an assertion from an untrusted device is worthless. Only the server can verify it against something it holds.
Authorize
Are you allowed to do this? A separate question from the first. You might be genuinely logged in and still have no right to see that post, because it belongs to a private account you don't follow. (These two words look almost identical and mean very different things — it's the most common beginner confusion in the whole field.)
Persist
Write it down permanently. "Persistent" storage survives the program stopping, the phone dying, the machine rebooting. If your like only lived in your phone's memory, it would vanish and nobody else would ever have known about it.
Database
A program specialised in storing data and answering questions about it quickly and reliably. INSERT like(88, 123) is roughly what such an instruction looks like: record that user 88 liked post 123.
Push notification
A message that appears on a device without that device having asked for anything. It goes through Apple's or Google's infrastructure, which is the only thing with a standing connection to every phone. You cannot reach your friend's phone. Nothing you write can. Only a server holding the right credentials can ask Apple to deliver it.

Analogy

Your phone is a customer at a bank counter. It can request things and be shown things. It cannot walk into the vault, cannot alter the ledger, cannot look up another customer's balance, and cannot phone a different customer at home. Those are all teller-side powers, and no amount of clever app code grants them, because they were never on your side of the counter to begin with.

If you try to condense down and strip it down — the responsibility and the use of backend to a single word — it will be this: data. The need to fetch data, the need to receive data, and the need to persist data somewhere.

Why it has to be centralised

If you look at your app, it is designed, it is customized according to your needs and your profile and all the people you follow. Similarly that is the case for your friend — they only receive the notification that is intended for them. But a server has to have all kinds of information, all kinds of state. So it has to be centralized.

Slices versus the wholeClients render personalised views; the server owns the truth and decides who sees which slice. That decision is authorization — and it's the reason "just do it on the frontend" collapses.

"State", "centralised", "single source of truth"

State is just "the current facts" — who follows whom, what's been liked, who's logged in. Anything that can change and has to be remembered.

Centralised means one authoritative copy in one place. The alternative — every phone holding its own copy — immediately breaks, because the copies would disagree the instant two people acted at once, and there'd be no way to decide who was right.

Single source of truth is the name for that one authoritative copy. When two systems disagree, this is the one that wins by definition.

And the consequence in the diagram's margin is the important one: if the server holds everything and the client decides which parts to show you, then anyone willing to modify their own copy of the app can simply decide to show themselves everything. The filtering has to happen on the side you don't control.

Analogy

A library holds every book; you leave with a few. If instead the library handed every visitor the entire collection and politely asked them to only read their own borrowings, "borrowing" would stop meaning anything. Sending data to a client and hiding it in the interface is exactly that mistake — and it's a real, frequent bug, not a hypothetical one.

Four

How frontends work

In order to understand why we can't use all those functionalities in the frontend, we have to see how frontends actually work behind the scenes. This is a Next.js application that I have deployed in the same AWS EC2 instance.

Next.js, waterfalls, chunks

Next.js
A popular framework for building websites with React. The relevant fact for this article: a Next.js site isn't a folder of files, it's a running program — a Node process listening on a port, exactly like the backend. That's why the two halves of this setup look identical.
React
A JavaScript library for building interfaces out of reusable components. All you need to know here is that it means the page is assembled by JavaScript running in your browser, rather than arriving finished.
Waterfall
The staircase-shaped chart in DevTools' Network tab. Each horizontal bar is one request; its left edge is when it started, its length is how long it took. Bars start late because the browser didn't know they existed yet — it had to read the HTML first to discover them. That dependency is what makes the staircase.
Chunk
One piece of a large JavaScript codebase, split up deliberately so the browser can download only what a given page needs instead of the entire application.
Favicon
The tiny icon in the browser tab. Its own separate request, like everything else.

The browser fetches the HTML file, and all the resources — for example all these JavaScript and all the images, the fonts and the CSS files — all of those different things are fetched in different requests after we have our primary HTML file.

Paint, then hydrateCSS arriving makes the page look correct. JavaScript executing makes it work. The window between them is why bundle size is an obsession in frontend performance.

Paint and hydrate — the two words in that diagram

HTML is the structure of a page (headings, paragraphs, buttons). CSS is its appearance (colours, spacing, fonts). JavaScript is its behaviour (what happens when you click).

Paint is the moment the browser has enough HTML and CSS to draw the page. It looks finished.

Hydrate is the later moment when the JavaScript has downloaded and run, attaching the behaviour to what's already drawn. Now the buttons do things. The name comes from the image of adding water to something dried out: the shape was already there, the life wasn't.

The gap between them is a real, visible interval — often a second or more on a slow phone — during which the page looks completely ready and completely ignores you. It's why frontend developers are obsessive about how much JavaScript they ship.

The DOM, which appears in the next section, is the browser's live in-memory model of the page. JavaScript changes the page by changing the DOM.

Analogy

A film set. Paint is the moment the shopfronts are up and it photographs as a real street. Hydrate is when the doors are actually connected to rooms. In between, everything looks right and nothing opens.

Five

Why backend logic can't live in the frontend

Whatever frontend logic that you have written, whatever JavaScript that you have written, is all fetched by the browser from our server and it is executed by the browser in the client's machine. So the browser is our runtime — compared to our traditional backends, where we sent a request, the server processed the request and sent us the result. It is exactly the opposite.

The asymmetry underneath all four wallsAnything running in a browser runs on hardware the user owns, in a runtime they can inspect. Secrets aren't secret. Logic isn't trusted. Client-side validation is a suggestion.

"The browser is our runtime"

A runtime is whatever environment your code executes inside. Backend code runs inside Node on a machine you rent. Frontend code runs inside a browser on a machine belonging to a stranger.

That relocation is the entire subject of this section, and it has a consequence people find hard to accept at first: every line of frontend code you write is public. It has to be — the browser can't run it without receiving it. Anyone can open DevTools and read it, pause it mid-execution, change a value, and resume. Not a hack; a standard feature of every browser, used by developers all day.

So an API key in frontend code is published. A check that says "only admins see this button" is a suggestion the user can delete. A price calculated in the browser is a number the user can edit before sending. None of this can be fixed with cleverness, because you don't own the machine.

Analogy

The backend is a sealed exam room you invigilate. The frontend is a take-home paper: you can print instructions on it, but the candidate is alone with it, holding a pen, and can write whatever they like before handing it back. So you check the answers when it returns — you never trust the paper to have marked itself.

Wall one · the sandbox

Browser runtimes are often sandboxed environments, which means they are isolated from our operating systems, the processes, and the file system. Everything is an isolated environment, which means the code can only access a limited amount of resources.

What the sandbox permits and forbidsEvery page you visit executes untrusted code from a stranger. The sandbox is what makes that survivable — and it forbids nearly everything a backend needs.

What's in the sandbox diagram

A sandbox is a restricted area a program runs inside, able to touch only what it's explicitly given. The name is literal: a child can do whatever they like in the sandpit without it affecting the garden.

Allowed: the DOM (the page itself), localStorage (a small key-value store the browser keeps per site, surviving refreshes), cookies (small pieces of data the browser automatically attaches to every request to a site — how logins persist), and fetch() (the function for making HTTP requests, subject to the CORS rules below).

Forbidden: reading your files; reading environment variables (settings passed to a program when it starts, the standard place to keep passwords and API keys on a server); opening raw TCP sockets (direct low-level network connections, as opposed to going through HTTP); seeing other programs on your computer; and binding a port — which is worth stating plainly, because it means browser code cannot be a server at all. It has no way to listen. It can only ever be the one asking.

HttpOnly, in that asterisk: a flag on a cookie meaning "JavaScript may not read this, only send it." It's how a session token can go with every request while remaining invisible to any malicious script that gets onto the page.

Essentially what a browser is doing is fetching code from a remote server and executing it in the user's browser. If it's not careful enough or isolated enough, the remote code can easily access data or files from the user's computer. Imagine you go to a website and you have no idea what the code of that website is — if browsers did not isolate environments, that code can easily get access to your file system, copy all your files, your sensitive details, and send it to their servers.

Wall two · CORS

You can imagine CORS as a policy — a security policy of browsers — which restricts JavaScript code to call external APIs which are not the same as the current domain.

Origin, and why this rule exists at all

An origin is the combination of scheme (https), host (frontend-demo.sriniously.xyz) and port (443). Change any one and it's a different origin, even if it looks nearly identical to a human.

The Same-Origin Policy says a script from one origin may not read responses from another. Here's why that's essential: your browser attaches your cookies to requests automatically. Without this rule, any random site you visited could quietly make a request to your bank, have your session cookie attached, and read your balance — from your own browser, fully authenticated. The rule doesn't protect the bank's server; it protects you from the page you're currently on.

CORS — Cross-Origin Resource Sharing — is the opt-out. It's the mechanism by which a server can say "actually, this specific other origin may read my responses." Despite the name, CORS relaxes the restriction; the restriction is the Same-Origin Policy.

Analogy

You're walking around carrying signed blank cheques (your cookies) that get used automatically. The Same-Origin Policy is the rule that a shop can only spend them on its own premises. CORS is the paperwork by which one shop explicitly authorises another to do so.

Same-Origin PolicyNote the third row: your own backend on a sibling subdomain is a different origin. This is why real apps have to configure CORS deliberately rather than it just working.

The preflight exchangeFor anything beyond a "simple" request the browser asks permission before sending the real one. The server's headers are the answer.

Three things people get wrong about CORS

It is enforced by the browser, not the server. curl ignores it entirely. CORS protects users, not APIs — it is not an access control mechanism and must never be treated as one.

It often does not stop the request being sent — it stops the response being read by the script. Side effects can still occur, which is precisely why CSRF tokens exist as a separate control.

Access-Control-Allow-Origin: * combined with credentials is invalid and browsers reject it. Reflecting the Origin header back without validating it is a common real-world vulnerability.

Preflight, and the three misconceptions above

A preflight is a small extra request the browser sends first, using the verb OPTIONS, asking permission before sending the real one. It exists because some requests cause changes — deleting something, say — and it would be no good discovering afterwards that you weren't allowed. A "simple" request (a basic GET, roughly) skips the preflight, since such requests were already possible before CORS existed.

Why "enforced by the browser" matters. CORS is a rule browsers voluntarily follow. The server sends headers; the browser chooses to obey them. curl, a Python script, or anything that isn't a browser simply ignores the whole system. So CORS can never protect an API from attackers — it only constrains scripts running in ordinary users' browsers. Treating it as access control is a genuinely dangerous mistake.

"Stops the response being read, not the request being sent." Subtle and important. For non-preflighted requests the server may have already acted before the browser blocks the reply. The attacker learns nothing, but the damage is done. CSRF (cross-site request forgery) is precisely that attack, and a CSRF token — an unguessable value the real page includes and a forged one can't know — is the separate defence needed for it.

* means "any origin." Combining it with credentials would mean "any site may make authenticated requests as this user," which is the exact catastrophe the policy exists to prevent, so browsers refuse. The tempting shortcut — reading whatever Origin the caller sent and echoing it back as permitted — is the same catastrophe wearing a disguise, and it happens constantly.

Wall three · databases

These drivers are written to work in environments that can handle socket connections, handle binary data, and maintain persistent connections. Things that browsers cannot do.

Driver, wire protocol, connection, pool

Driver
A small library that lets your program talk to a database. It translates your instructions into whatever format that particular database expects.
Wire protocol
The exact format of bytes sent over the connection. Databases use their own, not HTTP — designed for speed between trusted programs, not for the public web. Being binary, it can't be expressed as the text-over-HTTP that browsers are limited to.
Connection
An open, ongoing link to the database: authenticated once, then usable for many queries. Establishing one is genuinely expensive — a network handshake, encryption setup, a password check, and memory allocated on the database's side for your session.
Connection pool
A small set of those connections opened once at startup and reused forever. A request borrows one, runs its query, and returns it. Twenty connections can serve thousands of users a second, because each one only holds a connection for a few milliseconds.

Analogy

A pool is a rack of shared bikes at an office. Nobody buys a bike for a five-minute errand; you grab one, ride, put it back. Without a pool, every request buys and then destroys a bike. And the failure mode is the giveaway: it isn't that bikes get slow, it's that the shop can't build them fast enough and the queue collapses.

Database drivers speak binary wire protocols over raw TCP sockets, and browsers cannot open raw TCP. That alone settles it — but the connection pooling argument is the part most people haven't heard.

Backend servers maintain a list of connections — often called a connection pool — to our database server, so that it does not have to create and destroy connections again and again. Because backend servers receive thousands and thousands of requests in seconds, and if they do the connecting and destroying logic with each request, the database server is going to get overwhelmed.

Pooling, and the thing underneath itThe performance argument is real, but the security one is fatal: direct browser-to-database means handing out database credentials to everyone who loads the page.

Wall four · computing power

Frontend applications are everywhere. It could be a smartphone, it could be a desktop, it could be a laptop — and any kind of environment we can imagine, even a computer which has 256 MB of RAM and a single-core processor. The user might not have enough computing power to perform some heavy business logic, and things will start to lag and sometimes break because of the load.

Known hardware versus unknown hardwareCentralising heavy work means you only have to make one machine fast, and you can make it faster whenever you want.

Vertical and horizontal scaling

Scaling means handling more load. Vertical is a bigger machine — more cores, more memory. Simple, but there's a ceiling, and it usually means downtime to switch. Horizontal is more machines working in parallel, with something in front sharing the work out (a load balancer — a reverse proxy again, wearing a different hat). Harder to build, effectively unlimited.

Business logic — the phrase in the quote — means the rules specific to what your application actually does, as opposed to plumbing: how a price is calculated, whether a booking is valid, what a report contains. It's the part worth protecting and the part most likely to be expensive to compute.

The closing line is the one to keep: you can make your server twice as fast this afternoon. You cannot make your users' phones faster, ever.

All four together

Four independent walls, one conclusionAny one of these would be enough on its own. Together they mean the question isn't really "why not" — it's that there was never a path in the first place.

Six

The whole thing in one paragraph, then every word defined

The recap

You type an address. Your browser asks DNS what IP that name maps to, and gets back a number — usually from a cache, occasionally by walking a hierarchy of nameservers. It opens a TCP connection to that number on port 443 and negotiates TLS encryption. The packets reach Amazon, where a security group checks the destination port against a short allow-list and silently drops anything else. What survives arrives at one rented EC2 machine, where Nginx holds ports 80 and 443. Nginx decrypts the request, reads the Host header, matches it against its config files, and forwards the now-plaintext request over loopback to a Node process listening on port 3001 — a process kept alive by PM2, on a port the outside world cannot reach. That process queries a database through a pooled connection, builds some JSON, and hands it back. The reply retraces every hop in reverse, gets re-encrypted by Nginx on the way out, and appears in your browser. A second address on the same machine, differing only by one number in one config line, serves the frontend instead.

Decrypting at the proxy and forwarding plaintext internally.
Config
Text files controlling how a program behaves.
Process manager (PM2, systemd)
Keeps programs running: restarts after crashes and reboots, collects logs.
Docker / container / Kubernetes
Packaging an app with its dependencies; the sealed unit that results; the system for running many of them across many machines.
Scaling, vertical vs horizontal
Bigger machine vs more machines.
Load balancer
Distributes incoming requests across several machines.
curl
Command-line tool that makes an HTTP request and prints the raw response.
Frontend
HTML / CSS / JavaScript
Structure, appearance, behaviour.
DOM
The browser's live model of the page; JavaScript edits it to change what you see.
React / Next.js
A library for building interfaces; a framework built on it that also runs a server process.
Waterfall
The DevTools chart showing when each request started and how long it took.
Chunk / bundle
JavaScript split into pieces so each page downloads only what it needs.
Paint / hydrate
When the page looks right; when it starts working.
Runtime
The environment code executes in — Node on your server, the browser on theirs.
Sandbox
The browser's restricted environment: no file system, no env vars, no raw sockets, no listening ports.
localStorage
Small per-site storage in the browser that survives refreshes.
fetch()
The JavaScript function for making HTTP requests.
DevTools
The browser's built-in inspection panel. F12 or right-click → Inspect.
Security
Authentication vs authorization
Who are you, vs what are you allowed to do. Different questions, both server-side.
Origin
Scheme + host + port. All three must match to be "the same origin."
Same-Origin Policy
Browser rule stopping a script reading responses from another origin. Protects users.
CORS
The mechanism by which a server opts out of that restriction for named origins. Browser-enforced only.
Preflight
An OPTIONS request asking permission before sending a real one.
CSRF
Tricking a user's browser into making a state-changing request; countered by unguessable tokens.
XSS
Injecting malicious JavaScript into a page; countered largely by Content-Security-Policy.
Clickjacking
Invisibly embedding your page in another to steal clicks; countered by X-Frame-Options.
SSRF
Tricking a server into making a request on your behalf, often to reach internal resources.
IAM credentials
Cloud permission keys. The prize in most cloud breaches.
IMDS / IMDSv2
The EC2 self-metadata service and its hardened version requiring a token first.
DNS hijacking / cache poisoning
Changing a record at source; feeding a resolver a forged answer.
CVE
A publicly catalogued vulnerability with an ID number.
Information disclosure
Leaking software names and versions that make attacks easier to aim.
HSTS / CSP / X-Frame-Options
Three response headers: force HTTPS; restrict script sources; forbid embedding.
Brute force
Automated mass guessing of credentials. Constant on any exposed port 22.
Bastion / jump box
One hardened machine that's the only way in.

If you remember three things

One — a server is a process on a computer, listening on a port, and everything else is a way of getting a message to it. Two — the only public doors are 80 and 443; everything interesting listens on ports nobody outside can reach. Three — code in a browser runs on hardware you don't own, so nothing it holds is secret and nothing it checks is trusted. Every wall in section five is a restatement of that third fact.
