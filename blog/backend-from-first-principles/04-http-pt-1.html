Zero

Start here: what a protocol is

Post 03 traced a request from a browser to a process and treated the request itself as a sealed envelope. This post opens the envelope. If you're arriving cold, the only thing you strictly need from the previous post is that a client asks and a server answers, and that they find each other by IP address and port number.

Six ideas, before anything else

HTTP is not a program, a company or a piece of software. It is an agreement about the shape of text. Everything below follows from that.

1 · A protocol is an agreed format

Two computers that have never met need to exchange data. Neither can ask the other what its conventions are, because asking would itself require a convention. So the format is agreed in advance, written down publicly, and implemented by everyone. HTTP — HyperText Transfer Protocol — is that written-down agreement for the web. A browser made by Google and a server written by a stranger interoperate perfectly because both read the same document.

2 · HTTP is just text

This surprises people. An HTTP request in its classic form is plain readable text: a first line, some labelled lines, a blank line, and optionally a body. You could type one by hand. Later versions compress it into binary for speed, but the meaning is still that text — every diagram in this post shows the readable form.

3 · Request and response

One exchange, always in that order, always started by the client. The client's message is the request; the server's is the response. A single web page triggers dozens of these.

4 · Headers and body

Headers are labelled metadata lines — Name: value, one per line. The body is the payload underneath. A single blank line separates them, and that blank line is load-bearing: it is literally how the receiver knows the headers have ended.

5 · Method, path, status

Every request begins with a method (what kind of action: GET, POST…) and a path (which resource: /api/users/12345). Every response begins with a status code (how it went: 200, 404, 500). Those three fields carry most of the meaning of most exchanges.

6 · Resource

The generic word for "the thing being asked about" — a page, an image, a user record, a search result. HTTP deliberately avoids saying what a resource is; it only defines how you refer to one (a path) and what you may ask about it (a method).

The analogy this post runs on

HTTP is a standardised paper form. The top line says what you want and what you want done with it. Below that, a block of labelled fields about you and your preferences. Then a blank line meaning end of form. Then, if you're submitting something rather than requesting it, an attachment. The clerk sends back an identical-looking form: a result code at the top, labelled fields, blank line, attachment. Nothing more exotic than that is happening, ever.

One

The two core principles

The HTTP protocol serves as the primary medium through which web browsers and servers exchange data. Although various communication protocols exist, HTTP remains the most widely adopted standard for client-server interaction.

The opening sketch, redrawnThe cloud is not a network or a place. It is the protocol itself: the set of rules both ends already agreed to before the conversation started.

Everything else is consequenceTwo sentences. Nearly every design decision, limitation and workaround in web development traces back to one of them.

01

Statelessness

the server has amnesia by design

Statelessness means the server retains no memory of past client interactions. Every HTTP request must be self-contained, carrying all metadata — such as headers, URLs, and methods — required for processing. Once a server responds to a request, it immediately forgets the transaction and treats subsequent requests as completely independent events.

What "state" means, and why forgetting is deliberate

State is remembered context — the accumulated facts about an ongoing interaction. "You're logged in as Ada, you have three items in your basket, you're on step two of checkout." A stateful system holds that in memory for you. A stateless one does not.

Self-contained is the key word. Because the server has forgotten you, every single request has to re-introduce itself from scratch: who you are, what you want, what formats you accept. Nothing can be implied by what you said a moment ago, because from the server's point of view there was no moment ago.

This feels wasteful, and it is — the same authentication token is re-sent on every request, forever. The trade is deliberate, and section one's next diagram shows what you buy with it.

Analogy

A hotel concierge with perfect amnesia. Every time you approach the desk you must state your name, your room number and produce your key card — even if you spoke thirty seconds ago. Infuriating for a human, but it means any of the twenty concierges can serve you interchangeably, none of them needs to hand over notes at shift change, and if one faints mid-sentence you simply walk to the next desk and repeat yourself. That's the entire bargain.

Statelessness, its payoff and its billThe protocol refuses to remember, so a state management layer is bolted on top. Every login you have ever used is that layer, not HTTP itself.

The three state mechanisms, since they're easy to confuse

Cookie
A small piece of data the server hands the browser, which the browser then attaches to every subsequent request to that site, automatically and forever (until it expires). The automation is the point — and also the reason CSRF attacks work, as section seven explains.
Session
The cookie holds only a meaningless ID; the actual facts live server-side in a shared store the servers all read. Easy to revoke instantly. Costs a lookup on every request, and the store becomes something all your machines depend on.
JWT — JSON Web Token
"JAY-wot." The token itself carries the facts (user ID, role, expiry) plus a cryptographic signature proving the server issued it and nobody edited it. No lookup needed — which is what makes it fit the stateless model so neatly, and also means you cannot easily un-issue one before it expires.

Note that a JWT is signed, not encrypted: anyone holding one can read its contents. The signature proves authenticity, not secrecy. Putting anything private inside one is a classic mistake.

Security note · statelessness cuts both ways

Because identity is re-asserted on every request, the credential is in flight constantly — which is why HTTPS is non-negotiable and why token theft is so valuable to an attacker. A stolen session cookie or JWT is the user, with no further checks, until it expires.

It's also why logout is harder than it looks. With server-side sessions you delete the record and it's over. With self-contained JWTs there is nothing to delete — the token stays valid until its expiry regardless of what your app thinks. Real systems answer this with short lifetimes plus a refresh mechanism, or a revocation list, which quietly reintroduces the state you were avoiding.

02

The client–server model

one side asks, one side answers, never the reverse

The second core idea is the client-server architecture, where communication is always initiated by the client. The client (typically a browser or mobile application) sends a request specifying the desired resource, headers, and payload. The server listens for incoming connections, processes the request, and returns an appropriate response such as HTML, JSON, or media files.

The consequence people don't expect

The server cannot start a conversation. Ever. It has no way to say "by the way, you have a new message" — it can only answer questions it was asked. A server that wanted to notify you would have to wait, silently, for you to happen to ask.

This is a genuine limitation of HTTP, not an implementation detail, and it spawned an entire family of workarounds: polling (ask every few seconds, wastefully), long polling (ask, and let the server hold the line open until it has something to say), Server-Sent Events (one long-lived response the server dribbles data into), and WebSockets (abandon the request–response shape entirely and keep a two-way line open — the protocol named in post 03).

Every live-updating interface you have used is one of those four, working around a rule written into HTTP in 1991.

One rule, four industries' worth of workaroundsNotifications, live scores, collaborative documents and chat all exist in spite of this constraint rather than because of any feature of HTTP.

Two

What HTTP sits on top of

In general backend development, HTTP and HTTPS are conceptually interchangeable, as HTTPS simply adds an encryption and identity layer (TLS) over standard HTTP. Before exchanging data, the client and server must establish an underlying network transport connection. HTTP relies primarily on TCP to guarantee reliable, ordered data delivery without packet loss.

"Layer" — the idea underneath the diagram below

Networking is built as a stack of layers, each solving one problem and assuming the layer beneath already solved its own. HTTP gets to say "send this text to that server" without knowing anything about cables, routing or lost packets, because four layers below it have quietly handled all of that.

The value is that each layer can be swapped independently. HTTP doesn't change when you move from ethernet to wifi to 5G. And — as section three shows — HTTP/3 swapped out the transport layer beneath it without the shape of the messages changing at all.

Analogy

Posting a letter. You write the words (application layer). An envelope and address system get it to the right building (network layer). A courier company guarantees it arrives, in order, and re-sends anything lost (transport layer). Vans and roads physically move it (physical layer). You never think about the vans. If the courier switched from vans to bicycles, your letter would be unaffected — and that is exactly what HTTP/3 did.

The stack, and where HTTP sitsData travels down the stack on the way out and back up on the way in, each layer wrapping and then unwrapping the one above. HTTP occupies only the top rung — everything beneath it is machinery it never has to think about.

OSI, TCP, UDP, and the handshake

OSI model
A seven-layer reference diagram from 1984, used as shared vocabulary. Real networks don't map onto it perfectly — TLS famously sits awkwardly between layers 5 and 6 — but when someone says "a layer 7 firewall" or "layer 4 load balancer," this is the chart they mean. Treat it as a map, not a blueprint.
TCP
Transmission Control Protocol. Guarantees your bytes arrive complete and in order, re-sending anything lost. Reliable, and that reliability costs setup time.
UDP
The alternative: fire packets off with no guarantees, no ordering, no re-sends. Faster and simpler. Used where late data is worthless anyway — live video, games — and, as of HTTP/3, as the foundation the web is rebuilt on.
Three-way handshake
How a TCP connection opens. Client says "let's talk" (SYN), server says "agreed, and likewise" (SYN-ACK), client says "confirmed" (ACK). Three messages, so one full round trip before a single useful byte moves. On a connection with 100ms latency, that's 100ms of nothing.
TLS negotiation
Layered on top, adding its own round trips to agree on encryption and check the certificate. Historically this made HTTPS noticeably slower to start than HTTP — a cost later versions of the protocol went to great lengths to claw back.

Three

The evolution of HTTP

Thirty years, one obsessionEvery version is an answer to "why is this slower than it should be?" — never a change to what a request actually means.

In HTTP/1.0, every individual request required opening a new TCP connection, which introduced significant latency. HTTP/1.1 introduced persistent connections, allowing multiple request-response cycles over a single TCP connection along with chunked transfer encoding and improved caching.

Persistent connections and chunked encoding

Persistent connection (the Connection: keep-alive header from post 03) means: having paid for the handshake once, don't hang up. A page needing forty files pays the setup cost once instead of forty times. In 1.0 the cost was paid every single time, which on a 1996 connection was brutal.

Chunked transfer encoding solves a subtler problem. Normally a response says Content-Length: 4096 so the receiver knows when it's finished — but that requires knowing the size before you start sending. If the content is being generated on the fly, you don't. Chunked encoding lets the server send pieces, each prefixed with its own length, and a zero-length chunk to signal the end. It is what makes streaming a response possible at all.

HTTP/2 introduced multiplexing over a single connection, replaced plain text with binary framing, and added HPACK header compression and server push. HTTP/3 transitioned from TCP to the QUIC protocol (built on UDP), reducing latency, accelerating connection setup, and eliminating head-of-line blocking.

The four HTTP/2 words, then the HTTP/3 ones

Multiplexing
Many requests in flight simultaneously over one connection, their pieces interleaved and reassembled by an ID. In 1.1, one connection handled one request at a time — so browsers cheated by opening six connections per site, and developers cheated by mashing all their images into one giant sprite file. Multiplexing made both hacks obsolete.
Binary framing
The message is packed into structured binary frames instead of newline-separated text. Less ambiguous to parse, smaller, and faster. The cost: you can no longer read it off the wire with your eyes. The logical content is unchanged — your tools reconstruct the familiar text view.
HPACK compression
Headers repeat enormously — the same User-Agent, the same cookies, on every one of a page's eighty requests. HPACK keeps a shared table of headers already sent so subsequent ones are referenced by a tiny index instead of repeated in full. Note this is a direct tax rebate on statelessness.
Server push
The server pre-emptively sends files it knows you'll ask for next. The one apparent exception to "the server cannot speak first" — but only within a conversation you started. It proved hard to use well and has largely been abandoned in favour of hints telling the browser what to request early.
Head-of-line blocking
HTTP/2 multiplexed at its own level, but TCP underneath still insists on strict ordering: lose one packet and everything behind it waits, even parts belonging to unrelated requests. One dropped packet stalls the lot.
QUIC
The fix, and the reason HTTP/3 abandoned TCP. QUIC is built on UDP — which has no ordering rules to get in the way — and re-implements reliability per-stream, so a lost packet stalls only its own stream. It also folds the TLS handshake into the connection setup, cutting the round trips in the earlier diagram roughly in half.

Analogy

Head-of-line blocking is a single-lane road with a strict no-overtaking rule. One stalled car and the ambulance behind it waits too, however unrelated their journeys. HTTP/2 put more cars on the road; HTTP/3 finally added lanes.

Four generations of the same pictureWatch the red "setup" blocks disappear and the green work blocks pack tighter. That compression is the history of the protocol.

Why this matters practically

You will almost never write code that differs between HTTP/1.1, /2 and /3 — your framework and your reverse proxy handle it. What changes is which performance folklore still applies. Bundling files together, spreading assets across subdomains, and inlining images were all sensible in 2010 and are actively counterproductive over HTTP/2. Advice has a version number attached, even when nobody writes it down.

HTTP communication consists of two message types: request messages sent by the client and response messages returned by the server. An HTTP request message includes an HTTP method, target URL, protocol version, host header, request headers, and an optional body separated by a blank line.

Every line of the request, explained

PUT /api/users/12345 HTTP/1.1
The start line. Three fields separated by spaces: what action, on what resource, using what version. PUT means "replace this resource with what I'm sending." /api/users/12345 is the path — note it identifies a specific user by ID. Section six covers the methods properly.
Host: example.com
The one header that is mandatory in HTTP/1.1. This is the field Nginx read in post 03 to decide which site you wanted. The path alone isn't enough, because one machine serves many domains.
User-Agent
The client describing itself. The absurd string — claiming to be Mozilla, and Safari, and Chrome — is thirty years of compatibility lies fossilised: browsers impersonated each other to avoid being served degraded pages, and nobody dared stop.
Content-Type: application/json
What the body I am sending is. Without this the server would receive a pile of bytes and have to guess.
Content-Length: 123
How many bytes the body is, so the receiver knows when it has them all. The alternative is the chunked encoding from section three.
Authorization: Bearer eyJ…
The credential. Bearer is the scheme name and it means exactly what it says: whoever bears this token gets the access, no questions asked about who they are. The eyJ prefix is the giveaway of a JWT — it's what {" becomes in base64 encoding.
Accept: application/json
What I'd like back. Easy to confuse with Content-Type: Content-Type describes what you're sending, Accept describes what you want returned. This is content negotiation — the same URL can serve JSON or HTML depending on who asks.
Accept-Encoding: gzip, deflate, br
Compression formats the client can decompress. The server picks one and compresses the response, often to a quarter of its size. br is Brotli. This is an invisible, enormous performance win happening on nearly every request you make.
Referer: https://example.com/dashboard
Which page linked here. Famously misspelled in the 1996 specification and never corrected, because fixing it would break everything. A privacy leak by nature, which is why browsers now trim it.
Cookie: sessionId=abc123xyz456; lang=en-US
The state layer from section one, riding along automatically. The browser attached this without the page asking — which is precisely the behaviour CORS and CSRF defences exist to contain.

And the response's less obvious lines

200 OK
The status code plus a human-readable reason phrase. Only the number is meaningful to machines; the words are courtesy. The families: 1xx informational, 2xx success, 3xx redirect, 4xx you made a mistake, 5xx the server made a mistake. That 4 vs 5 split is the most useful distinction in debugging: it tells you which side to look at.
Cache-Control: no-store
"Do not save this anywhere, ever." Appropriate here because the response concerns one user's account. Get this wrong on a shared cache and one user's data gets served to another — a real and recurring class of bug.
X-Request-ID: abcdef123456
A custom header (hence X-) carrying a unique ID for this exchange, so it can be traced across every service and log file it touches. Invaluable at 3am. An example of the extensibility discussed in the next section.
Set-Cookie: … Path=/; Secure; HttpOnly
The server issuing a cookie. The flags matter more than the value: Secure = only ever send this over HTTPS. HttpOnly = JavaScript may not read it, only the browser may send it. Together they are the baseline defence for a session cookie, and their absence is a finding.
Vary: Accept-Encoding
A note to caches: "my answer depends on that request header, so don't reuse this copy for someone who sent a different one." Forgetting Vary is how a cache serves compressed bytes to a client that can't decompress them.

Analogy

The start line is the subject line of an email, the headers are the mail headers you never look at, the blank line is the gap before the message begins, and the body is the message. You have been reading this exact structure your whole life without noticing it.

Security note · the blank line is load-bearing

The separation between headers and body is defined by that one blank line, and by Content-Length telling the receiver where the body stops. When two servers in a chain — say a proxy and the app behind it — disagree about where one message ends and the next begins, an attacker can smuggle a second request inside the first. This is HTTP request smuggling, and it lets you sneak a request past the proxy's security checks entirely.

It is worth knowing simply as a reminder that parsing is security. A protocol made of text with ambiguous edges has been a source of serious vulnerabilities for thirty years — and is part of why HTTP/2's rigid binary framing is an improvement beyond speed.

Five

Why headers exist, and the five families

HTTP headers are key-value pairs transferred in requests and responses to communicate metadata about the message or the connection. Much like the address written on the outside of a shipping package, headers allow intermediaries and endpoints to inspect essential metadata without parsing the entire payload body.

The word doing the work here is "intermediaries"

An intermediary is anything between the two ends: a reverse proxy, a CDN, a corporate filter, a load balancer. A request typically passes through several. None of them should have to open and understand your body to do their job — a cache only needs to know how long to keep something, a proxy only needs to know which server to forward to.

Metadata is data about the data. The body is the content; the headers describe it. Keeping them separate is what lets a machine in the middle make a good decision cheaply, by reading a few hundred bytes instead of a few megabytes.

Analogy

The shipping label. The courier sorts, routes, prioritises and delivers your parcel using only what's printed outside — weight, destination, "fragile", "perishable". Nobody opens the box. And that's not merely polite: a sorting system that had to unpack every parcel to route it could not exist at scale.

The five slides, collectedThe grouping is a teaching aid rather than something the protocol enforces — but knowing which family a header belongs to tells you immediately who is meant to read it.

HTTP extensibility allows custom headers to be added without modifying the core protocol. Headers act as a remote control mechanism, enabling clients to negotiate content formats, authentication states, and caching parameters dynamically with the server.

The last two boxes — "extensibility" and "remote control"

Extensibility is the reason HTTP survived thirty years of the web changing beneath it. Anyone may invent a header. Receivers are required to ignore headers they don't recognise, so a new one can be deployed without breaking a single existing client. X-Request-ID was somebody's invention; so were the CORS headers before they were standardised. Most of the modern protocol started as somebody's custom header that caught on.

Remote control is the mental model for what headers do. They aren't passive labels — they're knobs each side turns to steer the other's behaviour without any code changing hands. Accept-Encoding tells the server to compress. Cache-Control tells every cache in the path how to behave. Content-Security-Policy restricts what the browser will execute. One end presses a button; the other end obeys.

Security note · why nosniff exists

Historically, browsers didn't trust Content-Type — they'd peek at the bytes and guess, because so many servers were misconfigured. That guessing is MIME sniffing, and it's exploitable: upload a file that a server labels as a harmless image, but whose contents look like JavaScript, and a sniffing browser may execute it. X-Content-Type-Options: nosniff turns the guessing off. One line, one whole attack class closed.

Note the pattern across the security family: every one of them is the server telling the browser to restrict itself. The server cannot enforce any of it. It can only ask, and rely on the browser being the one piece of software in this picture that is on the user's side.

Six

Methods, intent, and idempotency

HTTP methods explicitly define the semantic intent of an operation requested by a client on a server resource.

Five verbs, one ideaThe path says what; the method says what you intend to do to it. The same URL supports several methods, each meaning something different.

"Semantic intent" — and the thing nobody tells beginners

Semantics means meaning, as opposed to mechanics. Mechanically, every method is just a word at the start of a line. Nothing in HTTP prevents a server from deleting your account when it receives a GET. The method is a convention everyone agrees to honour.

That matters because the whole ecosystem acts on the convention. Browsers pre-fetch GET URLs speculatively. Caches store GET responses. Crawlers follow every link they see — all GETs. Proxies retry failed GETs automatically. If you build a "delete" link that performs its action on GET, a search engine crawler will eventually walk your site and delete everything. This has genuinely happened to real companies.

So the methods are not decoration. They are the contract by which every intermediary on the internet decides what it's safe to do with your request without asking.

An HTTP method is idempotent if executing it multiple times yields the exact same state on the server as executing it once. GET, PUT, and DELETE are idempotent because fetching, replacing, or deleting a resource repeatedly produces consistent side-effects. POST is non-idempotent because invoking it multiple times creates multiple independent resources.

The distinction that governs retriesNetworks lose replies. When a client doesn't hear back it must decide whether to try again — and idempotency is the only thing telling it whether that's safe.

Analogy

A lift button. Press it once or fifteen times, the lift is summoned — the state afterwards is identical. That's idempotent. Now compare the "buy" button on a checkout page: press it fifteen times and you own fifteen of them. That's not. And since neither button tells you whether your press registered, the difference between them is entirely a question of what it costs to press again.

Safe vs idempotent, and the PATCH footnote

A separate, narrower idea: a method is safe if it doesn't change anything at all. GET is safe. PUT and DELETE are idempotent but decidedly not safe. Every safe method is idempotent; the reverse isn't true.

PATCH sits awkwardly and is the standard exam question. It is not guaranteed idempotent, because it depends what your patch says. "Set status to archived" applied twice is harmless. "Add 10 to the balance" applied twice is a bug. Same method, different payload, different answer — which is why the specification declines to promise anything.

In practice, real systems that must not double-charge don't rely on method semantics at all. They use an idempotency key: the client generates a unique ID per intended action and sends it along, and the server remembers which keys it has already processed. Retry as often as you like; only the first one counts. Every payment API you will ever integrate works this way.

Seven

OPTIONS, the Same-Origin Policy and CORS

The sketch that names the whole mechanismCORS exists to turn a blanket "no" into a controlled "these ones, for these methods, with these headers."

The OPTIONS method checks allowed communication capabilities on a server, playing a critical role in Cross-Origin Resource Sharing. Browsers enforce the Same-Origin Policy, preventing web pages from making unauthorized requests to a domain different from the host origin. CORS is a browser-enforced security mechanism allowing servers to specify which cross-origin requests are permitted.

Origin, SOP, CORS — the three words, in the right order

Origin
Scheme + host + port. https://example.com (port 443 implied). Change any one of the three and it's a different origin — http://example.com, https://api.example.com and https://example.com:8080 are all different origins from it, and from each other. Note that a subdomain is a different origin, which catches everyone out.
Same-Origin Policy (SOP)
The default rule, on by default, in every browser: a script from one origin may not read a response from another. Nobody enables it; it simply is.
CORS
Cross-Origin Resource Sharing. The mechanism by which a server can say "this particular other origin may read my responses after all." Despite sounding like a restriction, CORS is the exception system — the relaxation, not the rule. Almost everyone gets this backwards on first encounter.

Why the Same-Origin Policy has to exist

Remember the Cookie header from section four: the browser attaches your cookies automatically, to every request to a site, without asking the page. Now imagine the rule didn't exist.

You visit some random blog. Its JavaScript quietly makes a request to your bank's API. Your bank cookie is attached automatically, so the bank sees a fully authenticated request and answers honestly. The blog's script reads your balance and posts it somewhere. You clicked nothing. Your bank did nothing wrong. Your browser did exactly what it was designed to do.

The Same-Origin Policy is what stands between you and that, on every page you have ever loaded. It does not protect the bank's server — the bank must still check permissions. It protects you from the page you happen to be on.

Analogy

Your cookies are signed blank cheques you carry everywhere, handed over automatically whenever a shop asks. The Same-Origin Policy is the law that a shop may only spend them on its own premises. CORS is the notarised letter by which one shop authorises a specific named other shop to do so too. And note who enforces the law: not the bank, but the wallet — your browser.

Two flows: simple and preflighted

Cross-origin requests follow either a simple request flow or a preflighted request flow. In a simple request flow, the browser attaches an Origin header to the request, and the server validates it against its CORS policy using Access-Control-Allow-Origin. If the header is missing or does not match the request origin, the browser blocks the response and throws a CORS error.

The simple flow, both outcomesThe two responses differ by exactly one line. Everything about whether your code works or throws a console error comes down to that line being present and matching.

The single most misunderstood point in this post

A CORS error does not mean the request was blocked. The request was sent. The server processed it. The response came back. The browser then refused to hand it to your JavaScript. If the request had a side effect, that side effect happened. CORS controls reading, not sending — and that gap is exactly the space CSRF attacks live in.

When a preflight is triggered

The trigger conditionsCondition three is why nearly every modern API call is preflighted: application/json isn't on the permitted list, so sending JSON is by itself enough.

Why those three conditions, of all things?

The rule is archaeological rather than logical. The "simple" cases are precisely the things a plain HTML <form> could already do in 1995, long before JavaScript could make requests. Those were already possible cross-origin, so forbidding them would have broken the existing web. Everything a form couldn't do — other methods, custom headers, JSON bodies — is new, and therefore gets the permission check.

So the dividing line isn't "dangerous vs safe." It's "already possible vs newly possible." Which is also why a cross-origin form POST still sails through with no preflight at all, and why CSRF remains a live concern despite CORS existing.

The full preflight exchange

The browser issues an initial preflight request using the OPTIONS method to query the server's supported origins, methods, and headers prior to sending the actual request payload. The server responds with HTTP 204 No Content along with headers specifying permitted origins, methods, non-simple headers, and cache duration. Upon preflight approval, the client transmits the original HTTP request and receives the final response payload.

# 1 — the preflight. Note: no body, and the real request has not been sent.
OPTIONS /api/resource HTTP/1.1
Host: api.anotherdomain.com
Origin: https://example.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: Authorization

# 2 — the server's answer. 204 means "no body, and none expected."
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://example.com
Access-Control-Allow-Methods: PUT, DELETE
Access-Control-Allow-Headers: Authorization
Access-Control-Max-Age: 86400

# 3 — approved, so now the browser sends what you actually asked for.
PUT /api/resource HTTP/1.1
Host: api.anotherdomain.com
Origin: https://example.com
Authorization: Bearer token123
Content-Type: application/json

{ "name": "John Doe" }

# 4 — and the real response. Still needs the Allow-Origin header.
HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://example.com
Content-Type: application/json

{ "message": "Resource updated successfully" }

Four messages where you wrote oneYour code called fetch() once. The browser turned that into two round trips. Access-Control-Max-Age is what stops it being two round trips every single time.

The five Access-Control-* headers

Access-Control-Request-Method / -Request-Headers
Sent by the browser on the preflight. "I'm about to send a PUT carrying an Authorization header — acceptable?" It's asking about a request it hasn't made yet.
Access-Control-Allow-Origin
The server's answer to "who may read this." Either one specific origin or *. It must also appear on the real response, not just the preflight.
Access-Control-Allow-Methods / -Allow-Headers
Which methods and which non-simple headers are permitted. If your request uses one not on the list, the browser stops before sending anything real.
Access-Control-Max-Age: 86400
Seconds the browser may cache this approval — here, 24 hours. Without it, every single API call costs two round trips instead of one. A genuinely significant performance header that people forget to set.
Vary: Origin
Not in the slide, but visible in the Burp capture and essential in practice. If your server varies its Allow-Origin per caller, caches must be told so — otherwise a cached response approving one origin gets served to another, and your policy quietly evaporates.

Three things people get wrong about CORS

It is enforced by the browser, not the server. curl, a Python script, Burp Suite and a mobile app all ignore it completely. CORS constrains scripts in ordinary users' browsers; it is not access control, and an API protected "by CORS" is not protected.

It blocks reading, not sending. Side effects can already have occurred by the time the browser refuses you the response. CSRF tokens exist as a separate control for exactly this reason.

Allow-Origin: * plus credentials is invalid and browsers reject it outright. The tempting workaround — read whatever Origin the caller sent and echo it straight back — defeats the entire mechanism while appearing to work perfectly, and is one of the most common real-world CORS vulnerabilities.

Seeing it for yourself

Burp Suite is an inspection tool used to intercept, visualize, and analyze live HTTP traffic between client applications and backend servers. By executing simple and preflighted requests in a web application environment, developers can inspect raw HTTP headers and status codes in real time to diagnose CORS configurations.

What a proxy tool is, and why it beats DevTools here

Burp Suite is an intercepting proxy: you point your browser at it, and every request passes through it on the way out. You see the raw bytes of both messages, and can pause, edit or replay them. DevTools shows you a tidied-up view of what the browser did; a proxy shows you what actually crossed the wire, including the requests DevTools hides.

For CORS specifically, this is the difference between seeing "CORS error, 0 B transferred" in DevTools and seeing the full OPTIONS exchange plus the real response that arrived and was then discarded. It is the most direct way to convince yourself that the request really was sent.

Why the tooling choice changes the conclusionIf you only ever look through DevTools it's easy to believe CORS stopped the request. Watch the same exchange through a proxy and the real behaviour — and the real risk — becomes obvious.

The practical checklist when CORS bites you

Is the failing request a preflight (OPTIONS) or the real one? Does Access-Control-Allow-Origin appear on both responses? Does it match your origin exactly — scheme, host and port? Is your method in Allow-Methods and every custom header in Allow-Headers? If you send cookies, is Allow-Credentials: true set and Allow-Origin a specific origin rather than *? Five questions, in that order, and they resolve nearly every case.

Recap, then every word defined

The whole post in one paragraph

HTTP is a publicly agreed text format for a client to ask and a server to answer. It rests on two rules: the server remembers nothing between requests, and only the client may speak first. Statelessness buys simplicity, horizontal scaling and resilience, and is paid for with cookies, sessions or JWTs re-sent on every single call. Underneath, TCP guarantees ordered delivery and TLS adds encryption — several round trips of ceremony that every HTTP version since 1996 has been trying to reduce, ending with HTTP/3 abandoning TCP altogether for QUIC. A message is a start line, headers, a blank line and a body; the start line carries the method and path going out and the status code coming back. Headers are metadata that intermediaries can act on without opening the body, grouped into request, general, representation and security families, extensible by anyone, and functioning as a remote control each side uses to steer the other. Methods declare intent, and their idempotency is what tells every proxy and client library whether a failed request is safe to retry. Finally, because browsers attach your cookies automatically, the Same-Origin Policy forbids scripts from reading other origins' responses, and CORS is the server-declared exception list — negotiated in advance by an OPTIONS preflight whenever the request is anything a 1995 HTML form couldn't already have sent.

Glossary

The protocol itself
HTTP
HyperText Transfer Protocol. A written-down agreement on the format of request and response messages.
HTTPS
The same protocol wrapped in TLS encryption. Conceptually identical for backend purposes.
Protocol
Any format agreed in advance so two parties who've never met can understand each other.
Stateless
The server retains no memory between requests; each must be self-contained.
State management layer
Cookies, sessions or JWTs — the mechanisms bolted on top to simulate memory.
Client–server model
The client always initiates; the server only ever responds.
Resource
Whatever a path refers to: a page, a record, an image, a search result.
Messages
Start line
The first line. Request: method, path, version. Response: version, status code, reason phrase.
Header
A Name: value metadata line. Any number of them, in either direction.
Blank line
The single empty line marking the end of the headers. Structurally essential.
Body
The payload. Optional — most GETs have none.
Status code
1xx informational · 2xx success · 3xx redirect · 4xx client error · 5xx server error.
Content negotiation
Client states preferences (Accept, Accept-Encoding) and the server picks a representation.
Chunked transfer encoding
Sending a body in self-describing pieces when its total size isn't known upfront. Enables streaming.
Request smuggling
Exploiting disagreement between two servers about where one message ends and the next begins.
Headers worth knowing by name
Host
Which domain the request is for. Mandatory in HTTP/1.1; how one machine serves many sites.
User-Agent
The client describing itself. Historically unreliable by design.
Authorization
The credential. Bearer means possession alone grants access.
Accept / Accept-Encoding
What formats, and what compression, the client can handle.
Content-Type / Content-Length / Content-Encoding
What the body is, how big, and how it's compressed.
Cache-Control
Instructions to every cache in the path. no-store means keep no copy anywhere.
ETag
A content fingerprint enabling cheap "has this changed?" checks.
Vary
"My answer depends on this request header" — tells caches not to over-share a response.
Set-Cookie
Issues a cookie. Secure = HTTPS only; HttpOnly = invisible to JavaScript.
Referer
Which page linked here. Misspelled in the 1996 spec, never fixed.
HSTS
Strict-Transport-Security: "never use plain HTTP with me again."
CSP
Content-Security-Policy: restricts which sources scripts may load from. Main anti-XSS control.
X-Frame-Options
Forbids other sites embedding your page in a frame. Anti-clickjacking.
X-Content-Type-Options: nosniff
"Believe my Content-Type, don't guess from the bytes."
Methods
GET
Retrieve. Safe and idempotent. Cached, prefetched, crawled and retried by things you don't control.
POST
Create, or "perform an action." Not idempotent — twice means twice.
PUT
Replace the whole resource. Idempotent.
PATCH
Modify part of it. Idempotent only if your patch happens to be.
DELETE
Remove. Idempotent — the second attempt changes nothing further.
HEAD
Exactly GET, but headers only, no body. Useful for checking existence or size.
OPTIONS
Ask what's permitted. In practice, the CORS preflight.
Safe
Changes nothing on the server. Only GET, HEAD and OPTIONS.
Idempotent
Doing it N times leaves the same state as doing it once. Governs whether retries are safe.
Idempotency key
A client-generated unique ID so the server can ignore duplicate submissions. How payment APIs avoid double charges.
Transport and versions
TCP
Reliable, ordered delivery. Costs a three-way handshake to open.
UDP
Fire-and-forget. No ordering, no retransmission, much less setup.
TLS
Encryption plus server identity verification. Formerly called SSL.
Three-way handshake
SYN, SYN-ACK, ACK — one full round trip before any data.
OSI model
The seven-layer reference chart. HTTP is layer 7; TCP is layer 4; IP is layer 3.
Persistent connection
Reusing one TCP connection for many requests. HTTP/1.1's headline feature.
Multiplexing
Many concurrent requests interleaved over one connection. HTTP/2.
Binary framing
Messages packed as binary frames rather than text. Faster and unambiguous to parse.
HPACK
Header compression using a shared table of previously-sent headers.
Server push
Sending resources before they're requested. Largely abandoned in practice.
Head-of-line blocking
One lost packet stalling everything queued behind it, related or not.
QUIC
A UDP-based transport with per-stream recovery and a merged TLS handshake. The basis of HTTP/3.
Origins, CORS and security
Origin
Scheme + host + port. All three must match to count as the same origin.
Same-Origin Policy
Default browser rule: a script may not read another origin's responses.
CORS
The server-declared exception list to that rule. Browser-enforced only.
Preflight
An OPTIONS request asking permission before sending the real one.
Simple request
Something a 1995 HTML form could already have sent. Skips the preflight.
Access-Control-Allow-Origin
"This origin may read my response." Required on the real response, not just the preflight.
Access-Control-Max-Age
How long the browser may cache a preflight approval. Halves your request count when set.
CSRF
Tricking a browser into sending a state-changing request with its cookies attached. Not prevented by CORS.
XSS
Injecting attacker JavaScript into a page. Countered chiefly by CSP.
Clickjacking
Invisibly framing a page to steal clicks. Countered by X-Frame-Options.
MIME sniffing
A browser guessing content type from bytes. Disabled with nosniff.
JWT
A self-contained signed token carrying its own claims. Signed, not encrypted — readable by anyone holding it.
Intercepting proxy
A tool like Burp Suite that shows and lets you edit the raw traffic your browser sends.

If you remember three things

One — HTTP forgets you between every request, and every login system you've ever used is a workaround for that. Two — the method isn't decoration; it's the contract by which caches, crawlers and proxies decide what they may do to your request without asking. Three — CORS blocks the browser from reading a response, not the server from acting on a request, and almost every misconception about web security starts by getting that backwards.
